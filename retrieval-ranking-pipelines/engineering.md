# 工程视角：推荐系统与 RAG 的多阶段漏斗

## 1. 先用四个问题判断一个阶段

看到“召回、检索、粗排、精排、重排”中的任何一个词，不要先背定义，先问：

1. **输入集合多大？**
2. **输出集合多大？**
3. **主要优化覆盖、精度，还是列表整体约束？**
4. **允许为每个候选花多少计算成本？**

多阶段系统的基本规律是：

```text
越靠前：
候选越多 → 单个候选计算越便宜 → 更重视覆盖和速度

越靠后：
候选越少 → 单个候选可以算得更细 → 更重视精度和整体体验
```

这是一条“计算预算逐级集中”的链路。

# 2. 推荐系统链路

## 2.1 系统位置

```text
用户、历史行为、当前场景
                +
            全量内容池
                ↓
┌──────────────────────────────┐
│ 多路召回 / Candidate Generation │
└──────────────────────────────┘
                ↓
        合并、去重、硬过滤
                ↓
┌──────────────────────────────┐
│      粗排 / Pre-ranking       │
└──────────────────────────────┘
                ↓
┌──────────────────────────────┐
│       精排 / Ranking          │
└──────────────────────────────┘
                ↓
┌──────────────────────────────┐
│  重排 / Re-ranking / Ordering │
└──────────────────────────────┘
                ↓
           最终展示列表
                ↓
       点击、停留、购买等反馈
```

候选规模会随业务变化。下面只是帮助理解的示意，不是行业固定标准：

```text
百万到十亿级内容
    ↓ 召回
数百到数万候选
    ↓ 合并、过滤
数百到数千候选
    ↓ 粗排
数十到数百候选
    ↓ 精排
几十个高分候选
    ↓ 重排
最终展示的几个到几十个 Item
```

## 2.2 多路召回

### 输入

- 用户 ID、用户画像
- 最近行为序列
- 当前页面、时间、地域、设备等上下文
- 全量 Item 索引

### 输出

来自不同召回通道的候选 Item 及其来源、初始分数。

### 为什么存在

全量内容可能达到百万、亿甚至更大规模。昂贵的精排模型不可能逐个计算所有用户—Item 对。

### 最重点解决什么

**确定候选集合：宁可多捞一些，也不要过早漏掉后续可能排得很高的优质内容，同时必须能在大规模数据上低延迟运行。**

### 常见召回通道

- 协同过滤召回：依据相似用户或共同行为。
- Item-to-Item：依据当前或历史 Item 找相似 Item。
- 双塔向量召回：分别编码用户与 Item，通过向量近邻搜索候选。
- 内容召回：依据文本、图像、类别或标签相似性。
- 热门召回：补充趋势内容。
- 关注关系召回：来自用户订阅、好友或创作者关系。
- 探索召回：主动给长尾或新内容曝光机会。

多路召回不是重复建设。不同通道覆盖不同的“可能相关”定义。

### 不用会怎样

直接对全量 Item 精排通常无法满足线上延迟和成本；如果只用单一路径，又容易形成覆盖盲区。

### 主要指标

- Recall@K：真实相关 Item 是否进入前 K 个候选。
- Hit Rate@K：每次请求是否至少命中一个相关 Item。
- 覆盖率：有多少 Item 或内容类别有机会被候选生成。
- 延迟、吞吐和索引成本。

## 2.3 合并、去重与硬过滤

### 输入

各召回通道返回的候选集合。

### 输出

合法、唯一、可以继续排序的候选集合。

### 主要动作

- 合并多个召回源。
- 对同一 Item 去重，并保留召回来源等特征。
- 过滤用户已经明确不喜欢或已消费的内容。
- 检查库存、地区、年龄、版权、权限和安全规则。
- 按业务要求保留或截断各通道配额。

### 最重点解决什么

**保证候选“有资格被排”，并把多路召回结果整理成统一输入。**

### 为什么不能完全交给模型

相关性模型回答的是“用户可能有多喜欢”，无法可靠替代“是否有库存”“是否有权限”“法律上能否展示”等确定性约束。

## 2.4 粗排 / Pre-ranking

### 输入

经合并和过滤后的较大候选集。

### 输出

规模更小、质量更高、可交给精排的候选集。

### 最重点解决什么

**在精排之前，用可控的计算成本淘汰明显较差的候选，实现效果与延迟之间的桥接。**

### 为什么需要

召回后的候选仍可能太多。精排模型往往需要读取大量在线特征并执行复杂交互，无法对全部召回结果运行。

### 常见做法

- 精排模型的轻量版本。
- 较少特征的浅层模型。
- 蒸馏模型。
- 向量点积或轻量交互模型。
- 结合计算成本约束的模型设计。

### 不用会怎样

- 候选较少时，可以没有独立粗排。
- 候选很多而精排昂贵时，跳过粗排会造成延迟、吞吐或成本不可接受。

### 主要指标

- 对精排高分候选的保留率。
- 与精排排序的一致性。
- 延迟、吞吐和特征读取成本。
- 上游误杀率。

## 2.5 精排 / Ranking

### 输入

粗排保留下来的较小候选集。

### 输出

每个候选的一个或多个预测分数，以及按目标函数排序后的列表。

### 最重点解决什么

**利用丰富的用户、Item、上下文和交叉特征，准确估计每个候选在当前请求中的价值。**

### 常见预测目标

- 点击概率
- 转化概率
- 观看时长
- 购买金额
- 用户满意度
- 长期留存或多目标价值

### 为什么比召回更精细

精排面对的候选少，可以使用：

- 更多实时特征
- 更复杂的用户行为序列
- 用户—Item 深度交互
- 多任务学习
- 校准后的价值函数

### 不用会怎样

只按召回相似度展示，通常无法充分区分“看起来相似”和“真正适合当前用户、当前场景”的候选。

## 2.6 重排 / Re-ranking / Post-ranking

### 输入

已经有预测分数和初始顺序的高质量候选列表。

### 输出

满足最终展示约束的列表。

### 最重点解决什么

**从列表整体而不是单个 Item 出发，修正“每项分数都合理，但整页体验不合理”的问题。**

### 常见目标

- 多样性：避免连续出现过于相似的内容。
- 新鲜度：适当提升新内容。
- 公平性：控制不同供给方或群体的曝光。
- 业务规则：广告间隔、类目配比、活动位。
- 探索与利用：给不确定但有潜力的内容机会。
- 去疲劳：抑制用户近期反复看到的内容。
- 列表级效用：考虑 Item 之间的互补或竞争。

### 不用会怎样

逐项预测分最高的内容可能高度同质、重复、过时，或违反列表级业务约束。

## 2.7 推荐系统的一句话记忆

```text
召回保“不漏”
粗排保“算得动”
精排保“判得准”
重排保“整页好”
```

# 3. RAG 链路

## 3.1 RAG 必须分成离线和在线

很多概念混淆来自把“建知识库”和“用户提问时检索”混成一条线。

### 离线建库链路

```text
数据源
  ↓
加载与解析
  ↓
清洗与结构保留
  ↓
Chunking
  ↓
元数据、权限、标题、摘要等增强
  ↓
Embedding
  ↓
关键词索引 / 向量索引 / 其他索引
```

### 在线问答链路

```text
用户问题与对话历史
  ↓
查询理解、改写、扩展或拆分
  ↓
Retriever 初检
  ├── BM25 / 关键词检索
  ├── Dense / 向量检索
  ├── Metadata Filter
  └── Graph / SQL / 其他数据源
  ↓
合并、去重、权限过滤、Fusion
  ↓
Reranker 精确相关性打分
  ↓
Context Selection / Packing
  ↓
Prompt = 问题 + 证据上下文
  ↓
LLM 生成
  ↓
引用、事实校验、Guardrail
  ↓
最终答案
```

规模同样只是示意：

```text
百万级 Chunk
    ↓ 初检
每路 Top 50～200
    ↓ 融合、去重
约 100～500 个候选
    ↓ Rerank
约 10～50 个高质量候选
    ↓ Context Packing
约 5～20 个互补 Chunk
    ↓
LLM 可用上下文
```

实际数字必须通过数据集、模型、上下文窗口、延迟和成本实验确定。

## 3.2 查询理解、改写与拆分

### 输入

用户原始问题和必要的对话历史。

### 输出

一个或多个更适合检索的独立 Query。

### 最重点解决什么

**修复用户表达与知识库表达之间的差异。**

常见问题：

- 指代依赖上文：“它有哪些缺点？”
- 口语和文档术语不同。
- 缩写未展开。
- 一个问题包含多个子问题。
- 问题过于宽泛或缺少关键限定。

查询改写发生在检索之前，它不是 Rerank。

## 3.3 初次检索 / Retrieval

### 输入

处理后的 Query 和索引。

### 输出

可能包含答案证据的候选文档或 Chunk。

### 最重点解决什么

**从大规模知识库中，以可接受的延迟找出高覆盖候选，让真正包含答案的证据进入后续阶段。**

### 常见路线

#### 关键词检索

- 典型方法：BM25。
- 优势：专有名词、产品编号、精确措辞往往很强。
- 局限：同义表达或语义改写可能匹配不到。

#### Dense / 向量检索

- Query 和 Chunk 分别编码为 Embedding。
- 通过向量相似度或 ANN 搜索 Top-K。
- 优势：能处理同义词和语义相近表达。
- 局限：精确字符串、罕见实体和细粒度关系未必稳定。

#### Hybrid / 混合检索

- 同时运行关键词和向量检索。
- 再用 RRF 或加权分数融合。
- 目标是结合词法精确性与语义泛化能力。

## 3.4 过滤、去重与融合

### 过滤

先处理确定性约束：

- 用户是否有权限访问
- 文档是否有效、过期或被删除
- 地区、租户、数据域是否匹配
- Chunk 是否达到最低质量要求

### 去重

避免同一文档的高度重叠 Chunk 占满候选集合。

### 融合

将 BM25、向量检索或多个知识源返回的结果组合成一个候选列表。

RRF 的直觉是：如果一个结果在多个召回列表中都排得较靠前，它更值得进入统一候选集。融合解决“多份排名怎么合并”，并不等同于理解 Query 与文档的深层语义。

## 3.5 Rerank

### 输入

Retriever 给出的几十到几百个候选 Chunk。

### 输出

按“是否真正有助于回答当前问题”重新排列后的候选列表。

### 最重点解决什么

**用更强的 Query—Chunk 联合建模，纠正初检只靠关键词或向量相似度带来的误排。**

### Bi-Encoder 与 Cross-Encoder

```text
Bi-Encoder：
Query 单独编码
Chunk 单独编码
→ 可预计算、可建索引、适合百万级初检

Cross-Encoder：
[Query, Chunk] 一起输入模型
→ 交互更充分、通常更准确，但每个候选都要重新计算
→ 适合对初检 Top-K 做 Rerank
```

因此最常见的组合是：

```text
Bi-Encoder / BM25 快速找 100 个
                ↓
Cross-Encoder 精细重排 100 个
                ↓
取前 5～20 个进入上下文
```

### 不用会怎样

初检分数高的 Chunk 可能只是主题相近，并不直接包含回答所需证据；这些噪声会占用上下文窗口并干扰生成。

## 3.6 Context Selection / Packing

### 输入

Rerank 后的高质量 Chunk。

### 输出

放入 Prompt 的最终证据集合及排列顺序。

### 最重点解决什么

**在有限 Token 预算内，选择足够、互补、低重复、可引用的证据。**

它不等同于简单取 Rerank Top-K，还可能处理：

- 去除高度重复 Chunk
- 为多子问题保留不同证据
- 扩展相邻 Chunk 以恢复上下文
- 保持文档顺序或来源分组
- 处理冲突证据
- 控制总 Token 数

从列表级职责看，它与推荐系统的“重排”更相似。

## 3.7 RAG 的一句话记忆

```text
改写让问题“更好搜”
检索让证据“进候选”
融合让多路“可合并”
Rerank 让证据“排得准”
Packing 让上下文“够用且不浪费”
生成让证据“变成答案”
```

# 4. 两条链路的对应关系

| 抽象职责 | 推荐系统 | RAG / 搜索 | 关键区别 |
|---|---|---|---|
| 全量对象 | 内容、商品、视频、广告 | 文档、段落、Chunk | 最终消费对象不同 |
| 请求表示 | 用户画像、行为和场景 | 用户 Query 与对话上下文 | 推荐可以没有显式文本 Query |
| 找候选 | 召回、Matching、Candidate Generation | Retrieval、Retriever | 本质都是大集合缩为候选集 |
| 多路整理 | 合并、去重、硬过滤 | Fusion、去重、权限过滤 | RAG 常需要融合 BM25 与向量结果 |
| 低成本筛选 | 粗排 / Pre-ranking | 初检打分、轻量筛选；不一定单列为粗排 | RAG 的命名通常没有统一“粗排”阶段 |
| 高精度判断 | 精排 / Ranking | Reranker | RAG 的 Rerank 在功能上常对应精排 |
| 列表级整理 | 重排 / Post-ranking | Context Selection / Packing | 一个面向展示列表，一个面向 LLM 上下文 |
| 最终消费 | 用户看到并交互 | LLM 读取后生成回答 | RAG 检索结果通常不是最终产品 |

# 5. 同一个词为什么会指不同位置

## Ranking

`Ranking` 既可以泛指“把对象排序”，也可以特指推荐系统中的精排阶段。

判断方法：

- 如果它接收几百个候选并运行复杂模型，通常是精排。
- 如果只是说“根据分数排序”，可能只是一个通用动作。

## Reranking

`Reranking` 的字面意思只是“再排一次”，没有规定必须解决哪种目标。

- 搜索/RAG：常用更昂贵的相关性模型重算候选。
- 推荐系统：常在预测分数之后加入列表级约束。
- 某些工程团队也会把“候选生成后的任何排序”统称 reranking。

因此不能只看名字，必须看输入、输出和目标。

## Recall

`Recall` 有两个含义：

1. 召回阶段：一个系统组件。
2. 召回率：一个评价指标。

“做召回”和“提高召回率”不是同一句话。

# 6. 端到端例子

## 6.1 短视频推荐

用户刚看完一条“露营装备”视频：

1. 多路召回分别找出相似视频、相似用户喜欢的视频、关注作者视频、热门户外视频和探索内容。
2. 合并并去掉重复、已看、不适龄或失效内容。
3. 粗排用少量特征从几千条缩到几百条。
4. 精排预测每条视频的点击、观看时长、点赞和负反馈概率，合成为价值分。
5. 重排避免连续十条都是同一帐篷测评，插入路线、烹饪和安全类内容，并控制作者重复度。
6. 最终展示列表。

如果一条好视频在召回阶段没有进入候选，后面模型再强也救不回来；这叫上游瓶颈。

## 6.2 企业制度 RAG

用户问：“出差改签的费用由谁审批？”

1. 查询改写补充公司制度语境，并保留“改签”“费用”“审批”等关键术语。
2. BM25 找精确出现“改签”的条款，向量检索找语义相近的差旅审批规则。
3. 权限过滤去掉用户无权访问的部门制度，融合两路结果并去重。
4. Cross-Encoder Reranker 判断哪些 Chunk 真正回答“谁审批”，而不是只讨论改签费用。
5. Context Packing 保留审批人条款、例外情况和生效日期，去掉重复段落。
6. LLM 基于这些证据给出答案和引用。

如果相关条款没有被初检捞到，Reranker 无法凭空创造它；如果初检捞到了但排得低，Reranker 才有机会救回来。

# 7. 工程实践原则

## 7.1 先测每一层，不只测最终结果

推荐系统：

- 召回：Recall@K、Hit Rate、覆盖率、延迟。
- 粗排：精排优质候选保留率、一致性、延迟。
- 精排：AUC、NDCG、校准、多目标预测效果。
- 重排：列表多样性、公平性、业务约束、在线指标。

RAG：

- 初检：Recall@K、Hit Rate、MRR、NDCG。
- Rerank：相对初检的 NDCG/MRR 提升和额外延迟。
- Context：证据覆盖、重复率、Token 使用率。
- 生成：正确性、忠实性、引用一致性和拒答能力。

## 7.2 候选集决定后续上限

下游只能重排已有候选：

```text
目标证据不在候选集
    ↓
Reranker 无法修复
    ↓
LLM 只能缺证据回答或拒答
```

推荐系统同理：精排无法选择召回阶段没提供的 Item。

## 7.3 不要用一个总分掩盖多目标

相关性只是一个目标。推荐和 RAG 都可能同时考虑：

- 时效性
- 权限与安全
- 来源可信度
- 多样性
- 长期用户价值
- 成本与延迟

应明确哪些是硬约束、哪些是模型分数、哪些是列表级目标。

## 7.4 术语必须绑定接口

团队文档中建议为每个阶段明确：

```text
阶段名：
输入对象：
输入规模：
输出对象：
输出规模：
打分方法：
硬约束：
核心指标：
延迟预算：
```

这样即使不同团队都叫“Rerank”，也能立即判断它们是否是同一个组件。
