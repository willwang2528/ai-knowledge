# 工程视角：召回、检索、粗排、精排与 Rerank

## 1. 统一判断方法

不要先看组件叫什么，先看四件事：

| 判断维度 | 要问的问题 |
|---|---|
| 输入 | 它接收全量对象、候选集，还是已有顺序的列表？ |
| 输出 | 它产出候选、分数，还是最终列表？ |
| 目标 | 它优先保证覆盖、精度，还是整体约束？ |
| 成本 | 它允许为每个候选花多少计算？ |

多阶段链路的共同规律：

```text
候选数量：多 ─────────────→ 少
单项成本：低 ─────────────→ 高
主要目标：覆盖 → 精度 → 整体可用
```

# 2. 推荐系统

## 2.1 数据链路

```text
用户、历史行为、当前场景
              +
          全量内容池
              ↓
多路召回 / Candidate Generation
              ↓
合并、去重、硬过滤
              ↓
粗排 / Pre-ranking
              ↓
精排 / Ranking
              ↓
重排 / Post-ranking
              ↓
         最终展示列表
```

候选规模示意：

```text
百万至十亿级 Item
  ↓ 召回
数百至数万
  ↓ 过滤、粗排
数十至数百
  ↓ 精排、重排
几个至几十个展示结果
```

具体数字取决于业务，不是行业标准。

## 2.2 召回 / Retrieval / Candidate Generation

| 项目 | 内容 |
|---|---|
| 输入 | 用户画像、行为、场景和全量 Item 索引 |
| 输出 | 一批可能相关的候选 Item |
| 核心目标 | 高覆盖、低延迟、大规模可运行 |
| 最怕的问题 | 优质 Item 没进入候选，后续无法补救 |

最重要的理解：

> 召回负责确定候选集合。宁可多捞一些，也不要过早漏掉优质内容，但“多捞”仍受延迟和下游容量限制。

常见召回通道只需理解其分工：

- 协同过滤：从相似用户或共同行为找候选。
- Item-to-Item：从用户刚看过的 Item 找相似对象。
- 双塔向量召回：根据用户向量与 Item 向量近邻搜索。
- 内容召回：根据文本、图像、类别或标签相似性。
- 热门、关注和探索召回：补充趋势、关系和长尾内容。

## 2.3 合并、去重和硬过滤

| 项目 | 内容 |
|---|---|
| 输入 | 多个召回通道的结果 |
| 输出 | 唯一、合法、可继续排序的候选 |
| 核心目标 | 解决资格和约束问题 |
| 典型规则 | 库存、地区、年龄、版权、权限、已消费、已删除 |

关键区别：

```text
过滤：这个候选能不能进入下一步？
排序：允许进入的候选谁更靠前？
```

权限和库存等硬规则不应依赖相关性模型碰运气。

## 2.4 粗排 / Pre-ranking

| 项目 | 内容 |
|---|---|
| 输入 | 召回并过滤后的较大候选集 |
| 输出 | 可交给精排的更小候选集 |
| 核心目标 | 在有限成本下淘汰明显较差候选 |
| 最怕的问题 | 算得太慢，或误杀精排真正会喜欢的候选 |

粗排的本质是“桥接计算预算”。常见实现是少特征轻量模型、蒸馏模型或轻量交互模型。

它不是固定算法：

- 候选少、精排便宜：可以没有粗排。
- 候选多、精排昂贵：可能有一层或多层粗排。

## 2.5 精排 / Ranking

| 项目 | 内容 |
|---|---|
| 输入 | 粗排保留的较小候选集 |
| 输出 | 候选价值分和初始顺序 |
| 核心目标 | 准确估计当前用户、当前场景下的候选价值 |
| 典型信号 | 用户行为序列、Item 特征、实时上下文和交叉特征 |

常见预测目标包括点击、观看时长、转化、购买和负反馈。精排可以使用比召回更丰富的特征和更复杂的模型，因为候选已经显著减少。

## 2.6 重排 / Re-ranking / Post-ranking

| 项目 | 内容 |
|---|---|
| 输入 | 已有精排分数和顺序的候选列表 |
| 输出 | 满足最终展示要求的列表 |
| 核心目标 | 优化列表整体体验，而不只是单个 Item 分数 |
| 典型约束 | 多样性、新鲜度、公平性、探索、作者和类目配比 |

例如，精排前十名可能都是同一作者的同类视频。每条单独看都合理，但整个列表体验很差；重排负责修正这种列表级问题。

## 2.7 推荐系统记忆句

```text
召回保“不漏”
粗排保“算得动”
精排保“判得准”
重排保“整页好”
```

# 3. RAG

## 3.1 离线建库

```text
数据源
  ↓
加载、解析、清洗
  ↓
切分 Chunk
  ↓
补充标题、元数据和权限
  ↓
生成 Embedding
  ↓
建立关键词索引 / 向量索引
```

离线链路决定“知识以什么粒度、什么表示被搜索”。它不属于用户提问时的 Ranking 流程，但会直接限制后续检索质量。

## 3.2 在线问答

```text
用户问题与对话历史
  ↓
查询理解、改写或拆分
  ↓
BM25 / Dense / Hybrid Retrieval
  ↓
权限过滤、去重、Fusion
  ↓
Reranker
  ↓
Context Selection / Packing
  ↓
LLM 生成、引用和校验
```

## 3.3 查询改写

| 项目 | 内容 |
|---|---|
| 输入 | 原始问题和必要对话历史 |
| 输出 | 一个或多个适合检索的独立 Query |
| 核心目标 | 修复指代、口语、缩写、歧义和复杂子问题 |

查询改写发生在检索之前，它不负责重排候选。

## 3.4 Retrieval

| 项目 | 内容 |
|---|---|
| 输入 | Query 和知识索引 |
| 输出 | 可能包含答案证据的候选 Chunk |
| 核心目标 | 让真正包含答案的证据进入候选集 |
| 最怕的问题 | 答案证据没有被找回，后续模型无从选择 |

三条常见路线：

| 方法 | 优势 | 主要盲区 |
|---|---|---|
| BM25 / 关键词检索 | 专有名词、编号和精确措辞 | 同义表达和语义改写 |
| Dense / 向量检索 | 语义相似和表达泛化 | 罕见实体、精确字符串 |
| Hybrid Search | 结合词法和语义覆盖 | 需要融合不同结果和分数 |

## 3.5 过滤、去重和 Fusion

- 权限过滤：用户是否能看到该文档。
- 有效性过滤：文档是否过期、删除或不属于当前数据域。
- 去重：避免多个重叠 Chunk 占满候选集。
- Fusion：把 BM25、向量或多个知识源的结果合成一个候选列表。

Fusion 解决“多份列表怎样合并”，Rerank 解决“候选怎样被更准确地判断”，两者不是一回事。

## 3.6 Rerank

| 项目 | 内容 |
|---|---|
| 输入 | Retriever 返回的几十到几百个候选 Chunk |
| 输出 | 按 Query—Chunk 相关性重新排列的列表 |
| 核心目标 | 区分“主题相似”和“真正能回答问题” |

常见两阶段组合：

```text
BM25 / Bi-Encoder
快速取得 Top-100
        ↓
Cross-Encoder
联合读取 Query 和每个 Chunk
        ↓
保留 Top-5～20
```

Bi-Encoder 可预计算候选向量，适合大规模初检；Cross-Encoder 交互更充分但每对候选都要重新计算，适合小规模精确重排。

因此，**RAG Reranker 在工程职责上更接近推荐系统精排**。

## 3.7 Context Selection / Packing

| 项目 | 内容 |
|---|---|
| 输入 | Rerank 后的高质量 Chunk |
| 输出 | 最终放入 Prompt 的证据集合 |
| 核心目标 | 在 Token 预算内保证证据足够、互补、低重复、可引用 |

它不一定只是机械取 Rerank Top-K，还可能：

- 去除高度重复 Chunk。
- 为多个子问题保留不同证据。
- 扩展相邻 Chunk 恢复语境。
- 保持来源顺序并控制总 Token 数。

从列表级职责看，它比 RAG Reranker 更接近推荐系统重排。

## 3.8 RAG 记忆句

```text
改写让问题“更好搜”
检索让证据“进入候选”
Rerank 让证据“排得更准”
Packing 让上下文“够用且不浪费”
生成让证据“成为答案”
```

# 4. 必要概念对照

只保留会影响整条链路理解的概念。

| 概念 | 是什么 | 最容易混淆的区别 |
|---|---|---|
| Retrieval | 从大规模集合取得候选的过程 | 是动作，不是评价指标 |
| 召回阶段 | 推荐系统对 Candidate Generation / Retrieval 的常见中文叫法 | 不是“召回率” |
| Recall@K | 相关对象中有多少进入前 K 个候选 | 是指标，不是系统阶段 |
| Matching | 计算请求侧和候选侧是否匹配 | 在推荐中常属于候选生成层 |
| Candidate Generation | 产生后续可评分候选 | 与推荐“召回层”通常同义 |
| Filtering | 删除无资格候选 | 判断能不能进，不判断谁靠前 |
| Fusion | 合并多个结果列表 | 合并列表，不等于深度相关性重打分 |
| Pre-ranking | 精排前的低成本筛选 | 由系统位置和成本定义，不是固定算法 |
| Scoring | 为候选计算数值 | 是排序依据，不等于完整列表优化 |
| Ranking | 泛指排序；在推荐阶段语境中常指精排 | 必须结合系统位置判断 |
| Re-ranking | 对候选再排一次 | RAG 常做相关性精排，推荐常做列表级调整 |
| Embedding | 对象的向量表示 | 是表示，不是检索动作 |
| ANN | 大规模向量近邻搜索 | 是检索算法类别，不是 Embedding 模型 |
| Bi-Encoder | Query 和候选分别编码 | 快、可建索引，交互较弱 |
| Cross-Encoder | Query 和候选联合编码 | 更准但更慢，适合 Rerank |
| Top-K | 按分数保留前 K 个 | 是截断操作，不是独立阶段 |
| Context Packing | 选择并组织最终证据 | 关注证据组合，不只是单项相关性 |

最关键的纠偏：

```text
中文“召回阶段” ≈ Retrieval / Candidate Generation
英文 Recall = 召回率指标

Retrieval 做动作
Recall 衡量结果
```

# 5. 两条链路对应关系

| 抽象职责 | 推荐系统 | RAG |
|---|---|---|
| 全量对象 | Item、视频、商品 | 文档、段落、Chunk |
| 请求表示 | 用户、行为和场景 | Query 和对话上下文 |
| 找候选 | 召回 / Matching | Retrieval |
| 整理多路结果 | 合并、去重、过滤 | Fusion、去重、权限过滤 |
| 低成本筛选 | 粗排 | 初检分数或可选轻量筛选 |
| 高精度判断 | 精排 | Reranker |
| 最终列表组织 | 重排 | Context Packing |
| 最终消费 | 用户直接浏览 | LLM 读取证据后生成答案 |

# 6. 工程实践

## 6.1 候选集决定下游上限

```text
目标对象没进入候选集
        ↓
下游无法重排或选择
        ↓
最终结果必然缺失
```

所以不能只评估最终点击或最终答案，还要单独评估 Retrieval。

## 6.2 每一层只承担明确职责

- 权限、库存等确定性条件放在硬过滤。
- 大规模候选覆盖交给 Retrieval。
- 精确相关性判断交给精排或 Reranker。
- 多样性和证据互补交给列表级整理。

把所有目标塞进一个总分，会使错误难以定位。

## 6.3 用接口定义术语

团队文档至少写清：

```text
阶段名：
输入对象与规模：
输出对象与规模：
核心目标：
使用的分数或规则：
延迟预算：
评价指标：
```

只要接口清楚，即使不同团队都叫“Rerank”，也能判断它们是否承担同一职责。

## 6.4 最小评估集合

| 阶段 | 优先关注 |
|---|---|
| 推荐召回 / RAG Retrieval | Recall@K、Hit Rate、覆盖率、延迟 |
| 粗排 | 优质候选保留率、延迟 |
| 精排 / RAG Rerank | NDCG、MRR、排序提升、额外延迟 |
| 推荐重排 | 多样性、公平性、业务约束和线上效果 |
| RAG Context | 证据覆盖、重复率、Token 成本 |
| RAG 生成 | 正确性、忠实性、引用一致性 |

## 后续可以研究的点

以下内容留作后续独立研究，本次不细究：

- **召回通道设计与训练**：决定系统覆盖边界。
- **粗排蒸馏与跨阶段一致性**：解决效果与推理成本的平衡。
- **排序学习目标**：比较 Pointwise、Pairwise 和 Listwise。
- **Hybrid Search 与 RRF**：解决词法和语义结果融合。
- **Reranker 模型选择**：比较 Cross-Encoder、Late Interaction 和 LLM Ranker。
- **列表级优化**：研究 MMR、DPP、多样性和公平性。
- **分阶段观测与实验**：建立端到端故障定位能力。
