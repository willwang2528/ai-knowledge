# 别再混淆召回、粗排、精排和 Rerank：用两条数据链路一次讲清

做推荐系统或 RAG 时，我们很容易遇到一组看起来相似的词：

召回、检索、Matching、Candidate Generation、粗排、精排、Ranking、Rerank。

单独看每个定义似乎都能理解，放在一起却总是混乱。原因不是这些词太难，而是同一个词在不同系统里可能承担不同职责。

真正有效的学习方法，是把它们放回数据链路。

## 一、为什么系统要分这么多层？

假设一个短视频平台有十亿条内容，但用户打开首页时只会看到十几条。

最准确的模型或许可以细致分析：

- 用户最近看了什么
- 当前时间和场景
- 视频内容和作者
- 用户与视频的复杂交互
- 点击、观看时长、点赞和负反馈概率

问题是，这样的模型不可能对十亿条视频逐一计算。

RAG 也是一样。知识库可能包含几百万个文本块，但 LLM 的上下文窗口只能接收少量证据。让最昂贵的语义模型逐一阅读全部文本，同样不现实。

所以两类系统都采用漏斗：

```text
先用便宜方法多找一些
          ↓
再用昂贵方法仔细判断
          ↓
最后组织成真正可消费的结果
```

这就是召回、排序和重排出现的根本原因：把有限的计算预算逐渐集中到少量高价值候选上。

## 二、推荐系统：召回保不漏，粗排保算得动，精排保判得准

一条典型推荐链路是：

```text
全量内容池
    ↓
多路召回
    ↓
合并、去重、硬过滤
    ↓
粗排
    ↓
精排
    ↓
重排
    ↓
最终展示列表
```

### 1. 召回：先决定“谁有资格进入候选”

召回也常被称为 Matching、Candidate Generation 或 Retrieval。

它最重要的任务不是给出最终顺序，而是：

> 从巨大内容池中，快速找出一批可能值得进一步判断的内容。

召回阶段更怕“漏”，而不是“多”。

因为一个优质视频如果没有进入候选集，后面的精排模型再聪明也看不到它。相反，多捞进来一些普通候选，后续还有机会淘汰。

当然，“宁可多捞”不等于把全量内容都返回。召回仍要受到延迟、吞吐和下游处理能力约束。

真实系统通常会使用多路召回：

- 根据相似用户行为召回
- 根据用户刚看过的 Item 召回相似内容
- 根据用户和内容向量做近邻搜索
- 召回关注作者的新内容
- 补充热门和探索内容

不同通道像不同猎手，从不同方向寻找可能的好内容。

### 2. 过滤：相关不代表可以展示

多路结果合并后，要先处理：

- 重复内容
- 用户已经看过或明确不喜欢的内容
- 库存、地区、版权、年龄和安全限制
- 已删除或失效内容

过滤回答的是“能不能进入下一步”，排序回答的是“谁更应该靠前”。二者不能混为一谈。

### 3. 粗排：为昂贵精排减负

召回后的候选仍可能有几千个，而复杂精排模型只能处理几百个。

粗排位于二者之间：

> 用相对便宜的模型，尽量不误杀好候选地缩小集合。

它的价值不在于给出完美顺序，而在于搭桥：既不能太慢，又要尽可能保住那些精排最终会喜欢的候选。

粗排不是固定算法名。候选集小、精排便宜的系统可能根本没有独立粗排；候选集巨大、精排昂贵的系统可能有不止一层粗排。

### 4. 精排：准确判断每个候选的价值

候选缩小后，系统终于可以读取更丰富的特征，并运行更复杂的模型。

精排可能同时预测：

- 点击概率
- 观看时长
- 购买或转化概率
- 点赞、收藏和负反馈
- 长期用户价值

然后把这些目标组合为最终价值分。

精排最重要解决的是：

> 在当前用户和当前场景下，这个候选到底有多值得展示？

### 5. 重排：单个都好，不代表放在一起也好

假设精排前十名全是同一个作者、同一类帐篷测评。每条单独看都很相关，但整页体验会非常单调。

重排从“整个列表”出发，处理：

- 多样性
- 新鲜度
- 公平性
- 作者和类目配比
- 探索机会
- 广告间隔和业务规则

因此可以这样记：

```text
召回保“不漏”
粗排保“算得动”
精排保“判得准”
重排保“整页好”
```

## 三、RAG：Retriever 找证据，Reranker 判证据，Packing 组证据

RAG 的在线链路可以写成：

```text
用户问题
    ↓
查询改写
    ↓
初次检索
    ↓
融合、去重、权限过滤
    ↓
Rerank
    ↓
Context Packing
    ↓
LLM 生成
```

### 1. 查询改写：用户会说话，不一定会写搜索词

用户可能问：“它有哪些缺点？”

这句话依赖上文，直接拿去搜索几乎没有意义。查询改写会结合对话历史，把它变成完整、独立、适合搜索的问题。

复杂问题还可能被拆成多个子问题，分别检索。

### 2. Retriever：先让答案证据进入候选集

RAG 初检通常包括：

- BM25 关键词检索
- Dense 向量检索
- 关键词与向量混合检索
- 元数据、图或结构化数据检索

它与推荐系统召回承担相同的抽象职责：

> 从大规模对象池中，快速得到高覆盖候选。

推荐系统的候选是 Item，RAG 的候选是文档或 Chunk。

### 3. Reranker：RAG 中的“精排”

向量检索可以快速找到语义相近文本，但“主题相近”不一定等于“能回答当前问题”。

例如用户问：“出差改签费用由谁审批？”

一个段落可能频繁出现“出差”和“改签费用”，却没有写审批人。它在初检中可能分数很高，但不应占据最终上下文。

Reranker 会把 Query 与每个候选 Chunk 放在一起，更细致地判断它是否真正有助于回答问题。

常见组合是：

```text
BM25 或 Bi-Encoder 快速找 Top-100
                 ↓
Cross-Encoder 精确重排这 100 个
                 ↓
取前 5～20 个作为证据候选
```

注意，这里的 Rerank 在功能上更像推荐系统的精排，而不是推荐系统最后处理多样性的重排。

### 4. Context Packing：最相关的前几段，不一定是最好的证据组合

即使 Reranker 已经给出相关性顺序，也不能总是机械取前五名。

前五名可能：

- 来自同一文档并高度重复
- 都只回答问题的一部分
- 缺少例外条款或时间条件
- 总长度超过上下文预算

Context Packing 要选择互补证据、控制重复、恢复必要上下文，并在 Token 预算内安排顺序。

从列表级职责看，它反而更像推荐系统的最终重排。

RAG 可以这样记：

```text
改写让问题“更好搜”
检索让证据“进入候选”
Rerank 让证据“排得更准”
Packing 让上下文“够用且不浪费”
生成让证据“成为答案”
```

## 四、不要再尝试给术语做机械翻译

最容易踩坑的是把名词做一一对应：

```text
Recall = Retrieval
Ranking = 精排
Rerank = 重排
```

这些翻译在某些语境成立，却不是普遍标准。

更可靠的判断方法是问五件事：

```text
输入是什么？
输入规模多大？
输出是什么？
核心优化目标是什么？
每个候选能花多少计算？
```

如果一个组件从百万文档中快速找一百个候选，无论团队叫它 Retrieval、Recall 还是 Matching，它都在承担候选生成职责。

如果一个组件对一百个 Query—Chunk 对执行昂贵联合建模，无论叫 Ranker 还是 Reranker，它都在承担高精度相关性判断职责。

如果一个组件根据多样性、权限和 Token 预算整理最终集合，它就在做列表级组织。

## 总结

这组概念背后其实只有一条主线：

> 大规模系统先追求覆盖，再追求精度，最后追求整体可用。

推荐系统：

```text
召回 → 过滤 → 粗排 → 精排 → 重排 → 展示
```

RAG：

```text
改写 → 检索 → 融合/过滤 → Rerank → Context Packing → 生成
```

只要把每个词放回数据链路，观察它接收什么、产出什么、候选规模如何变化、主要防止哪类错误，这些名词就不会再纠缠在一起。
