# 检索与排序多阶段链路

## 一句话定义

检索与排序链路是一种“逐级缩小候选集”的系统设计：前段用低成本方法尽量不漏掉好候选，后段在更小集合上投入更高计算成本，得到更准确、可控的最终结果。

## 为什么出现

无论是推荐系统还是 RAG，都面临同一个工程矛盾：

- 数据池很大，无法对每个对象运行最昂贵的模型。
- 用户只需要很少的最终结果。
- 既不能在前段过早漏掉好结果，也不能把大量噪声送到最终阶段。
- 最终结果不只要“相关”，还可能受到权限、多样性、新鲜度、安全性和上下文长度约束。

因此，真实系统通常不是“一个模型直接给答案”，而是一条多阶段漏斗。

## 核心问题

```text
大规模候选池
    ↓ 先保证覆盖：快、宽、宁可多捞
较大的候选集合
    ↓ 再提高精度：慢一些、看更多特征
较小的高质量集合
    ↓ 最后满足整体约束：顺序、规则、多样性
最终列表或生成上下文
```

最需要记住的不是术语，而是三种职责：

1. **找候选**：从“全部”变成“可能相关的一批”。
2. **判优先级**：判断候选之间谁更值得排在前面。
3. **整理最终列表**：处理单个分数无法表达的整体约束。

## 推荐系统完整链路

```text
全量内容池
    ↓
多路召回 / Matching / Candidate Generation / Retrieval
    ↓
合并、去重、硬过滤
    ↓
粗排 / Pre-ranking
    ↓
精排 / Ranking
    ↓
重排 / Re-ranking / Post-ranking
    ↓
最终展示列表
```

各阶段最核心的任务：

| 阶段 | 一句话职责 | 最怕什么 |
|---|---|---|
| 召回 | 确定候选集合：在巨大内容池中快速捞出一批“可能值得进一步看”的内容 | 过早漏掉优质内容 |
| 合并、去重、硬过滤 | 把多路候选整理成合法、唯一、可展示的候选集 | 重复、违规、不可用内容进入后续 |
| 粗排 | 用有限成本淘汰明显较差的候选，为昂贵精排减负 | 算得太慢，或误杀潜在优质内容 |
| 精排 | 用丰富特征和更复杂模型，准确估计每个候选对当前用户的价值 | 个体相关性判断不准 |
| 重排 | 从“整个列表”出发调整顺序，满足多样性、新鲜度、公平性和业务约束 | 单项分数虽高，但列表整体体验差 |

## RAG 完整链路

RAG 需要分成离线建库和在线问答两条链路。

### 离线建库

```text
原始文档
    ↓
解析与清洗
    ↓
切分 Chunk
    ↓
补充元数据与权限
    ↓
生成 Embedding
    ↓
建立关键词索引 / 向量索引
```

### 在线问答

```text
用户问题
    ↓
查询理解 / 改写 / 拆分
    ↓
初次检索：关键词、向量、混合或多数据源
    ↓
权限过滤、去重、结果融合
    ↓
Rerank：对候选 Chunk 做更精确的相关性重打分
    ↓
Context Selection / Packing：选择并组织最终上下文
    ↓
LLM 生成
    ↓
引用、校验与安全处理
    ↓
最终答案
```

各阶段最核心的任务：

| 阶段 | 一句话职责 | 最怕什么 |
|---|---|---|
| 查询改写 | 把用户语言变成更适合搜索的查询 | 原问题含糊、缺关键词或依赖对话上下文 |
| 初次检索 | 从大规模 Chunk 中快速取得高覆盖候选 | 答案证据根本没被捞出来 |
| 融合与过滤 | 合并多种检索结果，并移除无权限、重复或无效内容 | 多路结果不可比较或不合法 |
| Rerank | 用更强但更贵的模型重算“问题—Chunk”相关性 | 相似但不能回答问题的 Chunk 排在前面 |
| Context Packing | 在上下文预算内选出互补、足够且可引用的证据 | 重复、冲突或过长的上下文挤占窗口 |
| 生成 | 基于选定证据组织答案 | 脱离证据生成或引用不一致 |

## 最容易混淆的关键结论

### 1. 召回与 Recall 不是同一个语法层次

- “召回阶段”是一个系统步骤，也就是 Candidate Generation / Retrieval。
- “Recall@K”是评价这个步骤有没有漏掉相关对象的指标。
- 召回阶段追求较高 Recall，但也必须满足延迟和吞吐约束。

### 2. 检索与召回大体同类，但语境不同

- 推荐系统行业更常说“召回”，输入通常是用户及其上下文，输出是候选 Item。
- 搜索和 RAG 更常说“检索”，输入通常是 Query，输出是候选文档或 Chunk。
- 两者本质上都在做“大集合 → 候选集合”。

### 3. 粗排与精排是成本分层，不是固定算法名

- 粗排：候选较多，模型必须更轻、更快。
- 精排：候选较少，可以使用更多特征和更复杂的交互。
- 是否需要粗排，取决于候选规模、延迟预算和精排成本。

### 4. 推荐系统与 RAG 的 Rerank 含义不同

- 推荐系统的重排通常在精排之后，重点是列表整体约束。
- RAG 的 Rerank 通常在初检之后，重点是更准确地判断 Query 与 Chunk 的相关性。
- 因此，RAG 的 Reranker 在功能上更像推荐系统的“精排模型”。

### 5. 过滤不是排序

- 过滤回答：“这个候选能不能进入下一步？”
- 排序回答：“允许进入的候选谁更应该靠前？”
- 权限、库存、地区、年龄限制等通常是硬过滤，不应依赖相关性模型碰运气。

## 技术发展路线

```text
规则与关键词匹配
    ↓
协同过滤 / 统计召回 / BM25
    ↓
两阶段 Candidate Generation + Ranking
    ↓
Embedding 与双塔大规模检索
    ↓
粗排—精排—重排的工业级级联
    ↓
混合检索 + Cross-Encoder / Late Interaction Rerank
    ↓
跨阶段联合优化、列表级目标、Agentic Retrieval
```

## 我的理解

可以把整个系统想成招聘：

- 召回/检索：从百万份简历里，快速找出几千份可能合适的简历。
- 硬过滤：去掉没有合法资质、地点不符或重复投递的简历。
- 粗排：用较少信息筛出几百人。
- 精排：对几十或几百人做完整面试和综合评分。
- 重排：组建最终团队时，不只看个人分数，还要看技能互补、岗位配比和组织约束。

RAG 也一样，只是“候选人”变成了文档 Chunk，“最终团队”变成了送给 LLM 的证据组合。

## 未来方向

- 跨召回、粗排、精排阶段的联合优化，减少上游误杀和样本选择偏差。
- 用更高效的 Late Interaction 模型缩小“检索速度”和“交互精度”的差距。
- 把相关性、多样性、公平性、长期价值等目标做成可学习的列表级优化。
- RAG 从固定一次检索发展为按问题动态拆解、检索、验证和重试的 Agentic Retrieval。
- 从只评估最终点击或答案，转向分别评估每个中间阶段，定位质量瓶颈。
