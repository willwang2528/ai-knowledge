# RAG 模块链路：科研证据与技术路线

## 研究问题

论文研究的不是“RAG 是否有效”，而是：

> 当 RAG 已经被拆成多个可替换模块时，怎样在质量与效率约束下选择模块实现和组合？

## 技术路线

```text
建立模块地图
↓
分别比较每个模块的代表方法
↓
为每个模块保留少量候选和默认值
↓
固定其他模块，依次替换一个模块
↓
锁定当前优胜者并进入下一模块
↓
提出性能优先与效率均衡配方
```

这是一种顺序式、坐标式的贪心搜索。它降低了组合实验成本，但不能证明找到全局最优组合。

## 三个关键科研判断

### 1. 阶段最优不等于系统最优

独立重排实验中 `RankLLaMA` 的 `MRR@10` 最高，但端到端阶段选择了 `monoT5`。原因不是实验矛盾，而是端到端目标还包含生成质量和延迟。

同理：

- `HyDE + Hybrid` 赢得 mAP 和深召回，不代表它赢得 nDCG@10 或延迟。
- 生成式 `Recomp` 在局部压缩实验中平均 F1 最高，端到端实验实际比较的是 `Recomp` 抽取式。

### 2. 模块之间存在交互

论文一旦选定当前模块，就把它锁定给后续实验。这样会漏掉以下可能：

```text
某检索器 + monoT5 一般
但
同一检索器 + TILDEv2 + 不压缩 可能整体更好
```

换句话说，评价函数真正依赖完整配置：

```text
J(
  gate,
  retriever,
  reranker,
  repacker,
  compressor,
  generator
)
```

而不是每个模块各自独立的分数之和。

### 3. “最佳实践”必须绑定场景

论文自己承认推荐配方未必适用于所有任务和上下文。工程上至少要绑定：

- 目标语料和更新频率；
- 召回、排序、答案质量中的主指标；
- 延迟与成本预算；
- 生成器的上下文窗口和位置敏感性；
- 是否允许额外 LLM 调用。

## 代表论文

### Searching for Best Practices in Retrieval-Augmented Generation

- 年份：2024，EMNLP。
- 解决问题：RAG 模块多、组合复杂，工程选型缺少系统比较。
- 核心思想：建立模块化工作流，先做模块级比较，再在端到端链路中顺序替换。
- 贡献：给出从离线检索源到在线生成的模块地图，并同时讨论效果与延迟。
- 局限：贪心搜索、数据和指标不统一、部分推荐组合未完整验证、论文内部有数字口径冲突。

## 需要保留的原文矛盾

Discussion §5.1 声称性能优先组合的平均分是 `0.483`；Table 1 最终 `+ Recomp` 行显示：

```text
Avg Score = 0.446
Avg F1 = 0.354
Latency = 11.70s
```

原文没有提供足够说明来证明两者是不同指标或不同实验版本。因此正确处理方式不是选择一个数字，而是：

1. 同时保留两处原文记录；
2. 不把 `0.483` 当作已由 Table 1 直接验证；
3. 复现官方代码并逐列重算。

## 当前研究方向

本主题首次产出只保留三条直接延伸路线：

- 自适应 RAG：动态决定是否检索、检索多少和何时停止。
- 模块协同优化：联合训练或自动搜索检索、重排、压缩和生成。
- 面向生产的评测：把质量、延迟、成本、更新和可观测性放进统一目标。

## 后续可以研究的点

- 复现完整 `Hybrid + TILDEv2 + Reverse + Recomp` 效率配方。
- 使用统一数据、统一生成器和统一硬件重测所有模块。
- 比较贪心搜索、贝叶斯优化与多目标搜索的模块组合。
