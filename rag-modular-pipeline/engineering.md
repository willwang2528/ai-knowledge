# RAG 模块链路：工程拆解与方法表

## 先看系统位置

```text
离线：
Documents
→ Chunking
→ Embedding
→ Vector Database / Sparse Index

在线：
Query
→ Query Classification
→ Retrieval
→ Reranking
→ Repacking
→ Summarization / Context Compression
→ LLM Generation

支撑：
Fine-tuning → Generator
Evaluation → 全链路反馈
```

## 模块职责总表

| Module（中文） | Input → Output | 一句话解决的问题 |
| --- | --- | --- |
| `Chunking`（切块） | 文档 → 可检索文本块 | 决定系统能以什么粒度找到知识，同时平衡语义完整性与检索精度。 |
| `Embedding`（向量化） | 文本块 / 查询 → 向量 | 让不同措辞但语义相近的查询和文档可以被相似度匹配。 |
| `Vector Database / Index`（向量库 / 索引） | 向量和元数据 → 可搜索知识源 | 让系统在大规模语料中低延迟地执行近邻或混合搜索。 |
| `Query Classification`（查询分类） | 用户问题 → 检索 / 不检索 | 避免所有问题都检索，减少无效延迟和错误上下文。 |
| `Retrieval`（检索） | 查询 + 全量语料 → Top-k 候选 | 先在大规模数据上高召回地缩小候选集合，尽量不漏掉证据。 |
| `Reranking`（重排序） | 查询 + 候选 → 更准确的相关性顺序 | 对少量候选做更贵、更精确的判断，把真正相关内容排到前面。 |
| `Repacking`（文档重编排） | 已排序候选 → 重组后的上下文顺序 | 利用 LLM 对首尾位置更敏感的特点，决定证据在提示词里怎么摆。 |
| `Summarization`（摘要 / 上下文压缩） | 多篇候选 → 更短上下文 | 删除冗余和无关内容，控制上下文长度、噪声与生成成本。 |
| `LLM Generation`（生成） | 查询 + 证据 → 答案 | 综合外部证据作答，而不是只依赖模型参数记忆。 |
| `Fine-tuning`（微调） | 训练问题 + 不同质量上下文 → 更鲁棒生成器 | 让生成器学会从有用证据与噪声混合的上下文中提取答案。 |
| `Evaluation`（评估） | 模块 / 系统输出 → 指标 | 判断优化是否真的改善任务效果、检索能力、领域能力和延迟。 |

## 一、离线检索源

### 1. Chunking（切块）

最重要的问题：知识块过大，检索不够精确；知识块过小，证据会被切碎。

| 方法 | 一句话概述 | 优势和代价 |
| --- | --- | --- |
| `Token-level` 固定长度 | 按固定 `token` 数切分文档 | 实现简单、粒度可控；可能切断句子，没有通用最佳块大小。 |
| `Sentence-level`句子级 | 以完整句子作为切块边界 | 兼顾语义完整性、速度和实现复杂度；块长度可能不均。 |
| `Semantic-level`语义级 | 使用模型识别语义断点 | 边界自然、上下文连贯；切块成本高、实现复杂。 |
| `Small-to-big` | 使用小块匹配，返回包含它的大块 | 兼顾匹配精度与完整上下文；需要维护父子块映射。 |
| `Sliding Window`滑动窗口 | 在相邻块之间保留重叠上下文 | 减少边界信息丢失；增加索引冗余、重复召回与去重成本。 |
| `Chunk Metadata`块元数据 | 为知识块附加标题、关键词或假设问题 | 增加过滤与匹配信号；需要生成和维护元数据，端到端收益尚未验证。 |

### 2. Embedding（向量化）

最重要的问题：把查询与知识块放入同一语义空间，弥补关键词不一致。

| 方法族 | 一句话机制 | 论文是否实验 | 实验使用 / 结论 | 为什么好 | 证据 |
| --- | --- | --- | --- | --- | --- |
| `LLM-Embedder` | 用监督式语义表征匹配查询和文档 | 是 | **主链选用** | 在该 MS MARCO 设置下接近 `BGE-large-en`，模型规模约小三倍 | §3.2；Table 5 |
| `BAAI/bge` 系列 | 对比学习得到通用检索向量 | 是 | 多个尺寸进入 Table 5；未选为主链 | `bge-large-en` 分数略高，但模型更大 | Table 5 |
| `intfloat/e5` 系列 | 将检索任务统一为文本到文本向量匹配 | 是 | 进入 Table 5；未选 | 是候选嵌入族，但在论文特定设置中分数低于前两者 | Table 5 |
| `Jina-embeddings-v2` | 长文本向量模型 | 是 | 进入 Table 5；未选 | 支持较长文本；论文结果不能外推到所有版本和语料 | Table 5 |
| `GTE` 系列 | 通用文本嵌入 | 是 | 进入 Table 5；未选 | 工程可替换选项；仍需在目标语料重测 | Table 5 |
| `all-mpnet-base-v2` | Sentence Transformer 语义向量 | 是 | 进入 Table 5；未选 | 易用基线；在论文设置中表现较弱 | Table 5 |

注意：这里的“最好”只成立于论文使用的 `namespace-Pt/msmarco` 评测设置，不是 2026 年的通用模型榜单。

### 3. Vector Database / Index（向量库 / 索引）

最重要的问题：保存向量、文本和元数据，并在大规模语料上快速找近邻候选。

| 方案 | 论文比较方式 | 是否是性能实验 | 论文选择 / 一句话原因 |
| --- | --- | --- | --- |
| `Milvus` | 多索引、十亿级、Hybrid、Cloud-native 四项能力 | 否，只是功能矩阵 | **主链选用**；论文表中四项均满足。 |
| `Faiss` | 同上 | 否 | 作为本地向量索引库使用；论文表中不具备数据库式云原生与混合能力。 |
| `Weaviate` | 同上 | 否 | 生态选项；未进入端到端选型。 |
| `Qdrant` | 同上 | 否 | 生态选项；未进入端到端选型。 |
| `Chroma` | 同上 | 否 | 生态选项；未进入端到端选型。 |

证据：§3.3、Table 6。  
边界：Table 6 没有测吞吐、P99 延迟、召回率、内存、成本、过滤性能或运维复杂度，所以不能据此宣布 `Milvus` 是当前所有场景的最佳数据库。

## 二、在线主链

### 4. Query Classification（查询分类）

最重要的问题：判断当前问题是否真的需要外部知识。

| 方法 | 一句话机制 | 论文是否实验 | 实验使用 / 为什么好 | 证据 |
| --- | --- | --- | --- | --- |
| Always Retrieve | 所有问题都进入检索链 | 是，作为无分类对照 | 覆盖简单，但对翻译、改写等自包含任务增加延迟和噪声 | §4；Table 1 |
| Retrieval-need Classifier | 基于任务与输入信息充分性二分类 | 是 | **主链选用**；111K 样本、15 类任务，决定直接生成或进入 RAG | §3.1；Figure 2；Table 1 |

Table 1 中加入分类后，论文正文报告整体平均分从 `0.428` 到 `0.443`，延迟从 `16.41s` 降至 `11.58s`；但这些叙述数字与表格显示的部分值有差异，应复现核对。

工程风险：同一个任务是否需要检索还取决于知识时效、用户已给上下文和模型能力；生产系统需要置信度、回退策略和误判监控。

### 5. Retrieval（检索）

最重要的问题：从全量语料中取得一个“尽量不漏证据”的候选集合。

| 方法 | 一句话概述 | 优势和代价 |
| --- | --- | --- |
| `BM25`（关键词检索） | 依据词频和逆文档频率进行关键词匹配 | 擅长匹配专有名词、数字和稀有词；不擅长同义表达和语义匹配。 |
| `Contriever` / `LLM-Embedder`（向量检索） | 将查询和文档编码为向量，按照语义相似度检索 | 能匹配字面不同但语义相近的文本；需要运行嵌入模型并维护向量索引。 |
| `Query Rewriting`（查询重写） | 让 LLM 把原问题改写为更适合检索的表达 | 可以修复含糊或不完整的查询；增加一次生成调用，并可能导致查询语义偏移。 |
| `Query Decomposition`（查询分解） | 把复杂问题拆成多个子问题分别检索 | 适合需要组合多条证据的复杂问题；增加多次检索和结果合并的成本。 |
| `HyDE（假设文档生成）` | 先生成假设文档，再使用其向量检索真实文档 | 可以缩小查询与文档之间的表达差距；需要额外生成，并可能引入错误信息。 |
| `Hybrid Search`（混合检索） | 融合 `BM25` 关键词检索与向量检索结果 | 兼顾精确词项匹配和语义匹配；需要归一化不同检索分数并调整融合权重。 |
| `HyDE + Hybrid Search` | 使用假设文档增强查询，再融合关键词检索与向量检索 | 能进一步扩大候选证据覆盖范围；生成、检索和融合带来更高的计算与延迟成本。 |

关键数字：

| TREC DL19 / DL20 | `mAP` | `nDCG@10` | `R@1k` | 延迟 |
| --- | --- | --- | --- | --- |
| `HyDE` | `50.87 / 50.94` | **`75.44 / 73.94`** | `88.76 / 88.03` | `7.21s / 2.14s` |
| `Hybrid` | `47.14 / 47.72` | `72.50 / 69.80` | `89.08 / 88.04` | `3.20s / 0.77s` |
| `HyDE + Hybrid` | **`52.13 / 53.13`** | `73.34 / 72.72` | **`90.42 / 90.67`** | `11.16s / 2.95s` |

因此不能只说“`HyDE + Hybrid` 最好”：它赢在平均精确率和深召回，但前十排序质量不如 `HyDE`，延迟也更高。

### 6. Reranking（重排序）

最重要的问题：检索阶段重覆盖，重排序阶段用更精确的模型把真正相关证据推到前面。

| 方法 | 一句话机制 | 论文是否实验 | 独立实验表现 | 论文如何使用 / 为什么好 | 证据 |
| --- | --- | --- | --- | --- | --- |
| `monoT5` | 把 query-document 相关性转成 T5 文本判断 | 是 | `MRR@10 31.78`，`4.5s` | **主链和性能配方选用**；质量接近最高但远快于 `RankLLaMA` | §3.5；Table 10；Table 1 |
| `monoBERT` | 用 BERT 交叉编码 query-document | 是 | `31.69`，`15.8s` | 与 monoT5 接近但更慢，未选 | Table 10 |
| `RankLLaMA` | 用 Llama-2-7B 判断候选相关性 | 是 | **质量最高**：`32.35`，但 `82.4s` | 只适合质量预算极高的场景；不是最终端到端选择 | Table 10 |
| `TILDEv2` | 离线预计算文档词项概率，在线累加查询词得分 | 是 | **最快**：`27.83`，`0.02s` | **效率配方选用**；固定语料极快，但新文档需重新预处理 | §3.5；Table 10 |

阶段结论：

```text
单项质量最高：RankLLaMA
质量—效率折中：monoT5
固定语料最低延迟：TILDEv2
```

这三个结论不能合并成“monoT5 是所有意义上的最佳重排器”。

### 7. Repacking（文档重编排）

最重要的问题：候选已经确定，但 LLM 对上下文中间位置的证据利用较弱，因此还要决定文档摆放顺序。

| 方法 | 一句话机制 | 论文是否实验 | Table 1 平均分 | 论文选择 / 解读 |
| --- | --- | --- | ---: | --- |
| `Forward` | 按相关性从高到低排列 | 是 | `0.437` | 高相关文档在开头，但后面的 query 可能离它更远。 |
| `Reverse` | 按相关性从低到高排列 | 是 | **`0.446`** | **最终选用**；让高相关文档靠近末尾查询。 |
| `Sides` | 把高相关文档分布在首尾 | 是 | `0.443` | §3.6 的默认值；不是端到端最终胜者。 |

边界：三者差距很小，论文没有置信区间和显著性检验；`Reverse` 只能称为当前设置中的弱优胜者。

### 8. Summarization / Context Compression（摘要 / 上下文压缩）

最重要的问题：相关候选仍可能太长、有重复或有噪声，直接塞给 LLM 会增加成本并干扰作答。

| 方法 | 类型与机制 | 论文是否实验 | 局部实验平均 F1 / token | 论文使用 / 解读 | 证据 |
| --- | --- | --- | --- | --- | --- |
| No Summarization | 不压缩，直接使用候选 | 是 | `31.53 / 139` | 端到端平均分 `0.441`、`10.97s`；时延敏感时是合理选择 | Table 11；Table 1 |
| `BM25` | 抽取式；按关键词相关性选句 | 是 | `29.47 / 54` | 简单基线，未选 | Table 11 |
| `Contriever` | 抽取式；按稠密语义相关性选句 | 是 | `27.02 / 56` | 语义抽取基线，未选 | Table 11 |
| `Recomp` extractive | 抽取式；学习选择与查询有关的原句 | 是 | `30.87 / 51` | Table 1 实际采用；保留原文完整性 | §3.7；Table 11 |
| `SelectiveContext` | 非查询式；按信息量删除冗余单元 | 是 | `31.24 / 67` | 对照 query-aware 方法，未进入最终配方 | Appendix A.5；Table 11 |
| `LongLLMLingua` | 生成/重写式 query-aware 压缩 | 是 | `28.29 / 55` | 端到端更慢且可能扭曲语义，未选 | §3.7；Table 1、11 |
| `Recomp` abstractive | 生成式；将多文档合成为短摘要 | 是 | **`32.85 / 59`** | 局部平均 F1 最高，但 HotpotQA 低于不压缩 | Table 11 |

为什么最终不是一句“始终使用 Recomp”：

```text
端到端不压缩：Avg 0.441，10.97s
端到端 Recomp：Avg 0.446，11.70s
```

只有当上下文长度、噪声或 token 成本成为瓶颈时，`Recomp` 的压缩价值才更明确。

### 9. LLM Generation（生成）

最重要的问题：依据检索到的证据生成最终答案，并减少只凭参数记忆编造事实。

| 实验实现 | 一句话机制 | 为什么使用 | 证据 |
| --- | --- | --- | --- |
| Fine-tuned `Llama-2-7B-Chat` | 输入 query 与处理后的 documents，生成答案 | 固定生成器，便于比较前序模块；训练时加入相关和随机上下文 | §3.8；§4 |

论文研究的是前序 RAG 模块的组合，不是在比较不同生成模型，所以不能把结果直接外推到任意现代 LLM。

## 三、训练与评估支撑

### 10. Fine-tuning（生成器微调）

最重要的问题：真实检索结果并不纯净，生成器不能把所有上下文都当成真相。

| 图中方法 | 论文中的上下文构造 | 论文是否实验 | 结论 |
| --- | --- | --- | --- |
| `Normal` | `Dg`：只给相关文档 | 是 | 能学习使用正确证据，但对夹杂噪声的真实检索结果不够鲁棒。 |
| `Random` | `Dr`：只给随机文档 | 是 | 让模型看到无关上下文，但缺少“从噪声中挑出正证据”的训练目标。 |
| `Disturb` | `Dgr`：相关文档与随机文档混合 | 是 | **论文选用**；在 gold 或 mixed context 输入下总体最好。 |
| 重复相关文档 | `Dgg`：两份相同相关文档 | 是，但截图未列 | 用于区分“更多相关 token”与“噪声鲁棒性”。 |
| Base | `Mb`：不微调 | 是，但截图未列 | 基线。 |

为什么 `Disturb` 好：它模拟了“召回结果里既有正确证据也有干扰项”，训练目标与生产 RAG 更接近。

### 11. Evaluation（评估）

最重要的问题：防止只优化某个检索指标，却让最终答案、领域能力或延迟变差。

| 评估层 | 论文使用什么 | 解决什么 |
| --- | --- | --- |
| `General Performance`（通用能力） | 常识推理、事实核查、开放域 QA、多跳 QA | 判断接入 RAG 后基础任务是否真的改善。 |
| `Specific Domains`（特定领域） | Medical QA | 判断领域知识检索能否转化为领域答案质量。 |
| `Retrieval Capability`（RAG 专项能力） | Faithfulness、Context Relevancy、Answer Relevancy、Answer Correctness、Retrieval Similarity | 区分“没找到证据、证据无关、模型没用证据、答案错误”等不同故障。 |
| Efficiency（效率） | 每查询平均延迟 | 判断质量增益是否值得额外计算成本。 |

论文各阶段并非使用同一实验：

| 阶段 | 主要数据 / 指标 |
| --- | --- |
| Chunking | 单文档合成查询；Faithfulness / Relevancy |
| Embedding | MS MARCO 派生集合；MRR / Recall |
| Retrieval | TREC DL19/20；mAP、nDCG、Recall、Latency |
| Reranking | MS MARCO Passage Ranking；MRR、Hit Rate、Latency |
| Summarization | NQ、TriviaQA、HotpotQA；F1、token 数 |
| End-to-end | 多类任务；Acc、EM、F1、RAG score、Latency |

因此不能把不同表格的分数直接放在同一个排行榜里。

## 四、最终配方与验收判断

| 配方 | 模块组合 | 适用目标 | 证据强度 |
| --- | --- | --- | --- |
| Best Performance | Classifier → `HyDE + Hybrid` → `monoT5` → `Reverse` → `Recomp` | 质量优先，容忍 HyDE 的额外生成延迟 | 有逐模块端到端搜索过程支持，但仍是贪心搜索；Discussion 的 `0.483` 与 Table 1 的 `0.446` 冲突 |
| Balanced Efficiency | Classifier → `Hybrid` → `TILDEv2` → `Reverse` → `Recomp` | 固定语料、低延迟 | 各组件有局部证据，但完整组合没有单独端到端报告 |

上线时至少记录：

```text
每阶段输入/输出数量
检索 Recall@k 与 nDCG@k
重排前后正例位置变化
最终上下文 token 数
答案正确性与忠实度
每模块 P50 / P95 / P99 延迟
每次请求的模型调用和成本
```

## 后续可以研究的点

- 检索门控的置信度、回退与误判成本。
- Query Decomposition 在多跳任务中的真实价值。
- 动态选择 `monoT5` / `TILDEv2` 的分层重排策略。
- 不同上下文窗口与位置偏差下的 Repacking。
- 端到端全局搜索和完整效率配方复现。
