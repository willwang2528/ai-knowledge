# 别再把 RAG 只理解成“向量检索”：一条请求到底经过了什么？

## 背景问题

很多 RAG 架构图只有三步：

```text
问题 → 检索 → LLM
```

这个描述没有错，却隐藏了真正决定系统效果的细节。

文档要怎么切？问题是否一定需要检索？第一批候选如何取得？候选怎样精排？文档以什么顺序放进提示词？上下文是否应该压缩？

这些选择共同决定最终答案，而不是某一个向量模型单独决定。

## 为什么重要

当答案出错时，“检索不准”往往只是一个模糊描述。

真实故障可能发生在完全不同的位置：

- 切块切断了关键证据；
- 检索阶段漏掉了正确文档；
- 重排序没有把正确证据推到前面；
- 文档位置让 LLM 忽略了中间证据；
- 压缩器删掉或改写了关键事实；
- 生成器没有学会从噪声中使用证据。

只有先看到完整链路，才能知道该优化哪里。

## 核心思想一：Retrieval 是候选召回

在 RAG 中，`Retrieval（检索）` 的任务是：

> 从百万级甚至更大的语料中，快速取得一批可能相关的候选，重点是不要过早漏掉正确证据。

关键词检索 `BM25` 擅长名字、数字和稀有词；稠密检索擅长同义表达和语义关系。`Hybrid Search` 把两者结合，利用它们的互补性。

论文进一步测试了 `HyDE`：先让模型生成一篇假设文档，再用这篇文档去寻找真实文档。它可以缓解“用户问题很短，而目标文档写得很完整”的表达差距，但会增加一次生成调用。

因此，`HyDE + Hybrid` 取得更高的 mAP 和深召回，并不代表它在所有意义上最好。它的前十排序指标不如单独 `HyDE`，延迟也更高。

## 核心思想二：Reranking 和 Repacking 不是一回事

`Reranking（重排序）` 仍然在判断相关性：

```text
几十个候选
→ 用更精确、更昂贵的模型逐个判断
→ 把真正相关文档排到前面
```

论文的独立实验给出三个预算档位：

- `RankLLaMA`：质量最高，但非常慢；
- `monoT5`：质量与延迟折中；
- `TILDEv2`：固定语料下极快，但需要离线预计算。

`Repacking（文档重编排）` 则不再改变相关性分数。它只决定文档在 LLM 上下文中的位置。

论文比较：

- `Forward`：高相关文档在前；
- `Reverse`：高相关文档在后、靠近问题；
- `Sides`：高相关文档分布在首尾。

`Reverse` 在当前实验中略高，但三者差距很小。它是一条值得验证的启发式，不是永远成立的定律。

## 核心思想三：压缩不是默认必开

上下文压缩听起来总是正确：删掉冗余，节约 token，让 LLM 更聚焦。

但压缩器也可能：

- 删除必要证据；
- 改写原文语义；
- 增加额外延迟。

论文端到端实验中，不压缩与 `Recomp` 的平均分分别为 `0.441` 和 `0.446`，延迟分别为 `10.97s` 和 `11.70s`。增益很小。

更稳妥的工程规则是：

> 只有上下文长度、噪声或 token 成本已成为瓶颈时，才启用并验证压缩器。

## 工程案例

假设企业知识库问答经常漏掉产品型号：

```text
先检查 Retrieval：
BM25 是否保留了型号、版本号等精确匹配信号？

再检查 Reranking：
正确文档是否已经召回，只是排位太低？

再检查 Repacking：
正确文档进入了上下文，但是否落在模型不敏感的位置？

最后检查 Compression / Generation：
关键型号是否被压缩器删掉，或生成器没有引用证据？
```

同一个“答案错误”，对应的是四类完全不同的修复。

## 未来趋势

下一步不是给每个模块永久指定一个模型，而是让系统根据请求动态选择：

- 简单问题跳过检索；
- 精确词项问题提高 BM25 权重；
- 高价值复杂问题启用 HyDE 与重型重排器；
- 低延迟请求使用 Hybrid 与轻量重排；
- 只有上下文超限时才压缩。

## 总结

理解 RAG，最重要的是记住这条因果链：

```text
切块决定“能检索什么”
检索决定“候选有哪些”
重排序决定“谁更相关”
重编排决定“证据放哪里”
压缩决定“哪些内容留下”
生成器决定“如何基于证据回答”
```

只要链路清楚，`retrieval`、`reranking`、`repacking` 就不会再混在一起。

## 后续可以研究的点

- 自适应检索与动态路由。
- 多跳问题的查询分解。
- 面向延迟和成本的分层重排。
